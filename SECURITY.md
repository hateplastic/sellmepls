# Проверка безопасности — 16 октября 2026

Это инженерная проверка приложения и интеграции, не независимый аудит и не гарантия отсутствия уязвимостей. Локальная конфигурация переведена на mainnet по запросу владельца. RPC Solana mainnet, Supabase, R2 и создание заказа проверены; реальный перевод и последующая выдача файла ещё не проверены владельцем. Контракты EVM этого экземпляра ещё не развёрнуты; их создание через кошелёк доступно в админке.

## Что проверено

Проверка 16 октября: 218 автоматических тестов, TypeScript и production-сборка прошли (полный запуск 217 тестов и повтор 7 тестов Solana после добавления одного случая нулевой партнёрской выплаты). Публикация, заказ и склад проверены на подключённых Supabase/R2; тестовые записи и файлы удалены. Поиск «тг» + категория «Софт» + сортировка по цене проверены ранее; количество 30 × 0.10 = 3 USDC проверено в браузере. Реального перевода в блокчейн в этих проверках нет.

- Автоматические тесты покрывают расчёт комиссии и партнёрских выплат, негативные сценарии контрактов и проверки транзакций, RLS, защиту чужих заказов, редактор, приватный чат, доступ администратора, галерею, обработку YouTube URL и разделение окружений.
- Реальная Supabase принимает подписанные сообщения EVM/Solana, сформированные тем же кодом, что использует сайт. Пользователь дополнительно подтвердил успешный вход через MetaMask, Phantom EVM и Phantom Solana после исправления.
- Реальный сценарий через локальные HTTP routes и Server Actions: регистрация временных кошельков, загрузка ZIP в R2, публикация, редактирование, замена на PDF, отказ чужому продавцу и устаревшей версии, скачивание неизменённых байтов по ссылке на 15 минут. Созданные тестом записи и файлы удалены.
- Дополнительно проверены публикация галереи, выдача превью и сохранение фото/YouTube при замене ZIP на PDF. Видео хранится как проверенный 11-символьный ID, произвольный HTML и iframe URL от продавца не принимаются. Плеер youtube-nocookie загружается только после клика.
- Mainnet checkout проверен временными пустыми Solana/EVM-кошельками с одного компьютера: корректный отказ при чужом типе сети, покупке собственного товара, совпадении выплат продавца с платформой; успешное создание заказа 0.60 USDC (0.06 платформе / 0.54 продавцу), повтор без дубликата. Подготовка транзакции через Helius прошла; намеренно подменённый и подписанный временным кошельком перевод отклонён до broadcast. Попытка скачать неоплаченный товар не выдаёт URL; прямой UPDATE статуса продажи запрещён RLS. Переводов в сеть не было; записи теста удалены.
- Чат проверен на реальных аккаунтах теста: до покупки, сохранение истории, защита от повторной отправки, запрет чтения/отправки третьему пользователю, включая прямой запрос к Supabase с его токеном.
- Админка проверяет подписанную identity через Supabase `getUser()`. Адреса выплат в профиле и `user_metadata` не дают права администратора. Пустой серверный allowlist закрывает доступ всем. Аналитический RPC недоступен `anon` и `authenticated`.
- Клиентские bundles проверены на наличие значений серверных секретов: совпадений не найдено. `/.env.local` возвращает 404. `npm audit --omit=dev` не нашёл известных уязвимостей на дату проверки; это не проверка логических ошибок.

## Защита платежей и файлов

Склад хранит каждую строку отдельно в AES-256-GCM с привязкой к товару и отпечатку строки. `INVENTORY_ENCRYPTION_KEY` хранится только на сервере; его необходимо резервировать вместе с данными. У `inventory_units` включён RLS, чтение/запись доступны только сервисной роли. Исходный TXT не становится скачиваемым товаром. Покупатель получает только строки оплаченного заказа, причём повторная загрузка возвращает тот же набор. Резервирование и назначение строк атомарны, дубликаты внутри товара исключаются, включая уже проданные строки. Интеграционный тест проверил конкурентное резервирование, доступ другого покупателя, отказ неоплаченному заказу, пополнение и выдачу ровно 30 назначенных строк. Завершение оплаты в этом тесте моделировалось только для тестовой записи, а не подтверждалось реальным переводом.

Worker возвращает истёкший резерв только после проверки, что выданный платёж уже не может завершиться: для Solana учитываются выданные blockhash, финализированная высота и история покупателя; для EVM — срок и mapping оплаты router. При недоступном RPC, неполной истории или неоднозначном результате резерв сохраняется. Ограничения и восстановление описаны в `INVENTORY.md`. Проверка на mainnet без отправки отдельно подтвердила готовность SOL-заказов на 0.0001 и 0.001 SOL; она не заменяет реальный тест владельца.

Тариф версии 2 применяется только к новым заказам: 10% при стоимости строго ниже $2.50, иначе 5% + $0.50. Проверки PostgreSQL независимо подтверждают процент, фиксированную часть и USD-порог по сохранённому курсу. Значение токена для USDC/USDT фиксировано в $1; подмена курса для обхода порога отклоняется. Старые записи сохраняют версию 1. Поиск каталога вызывается сервером через параметризованный RPC; поисковые операторы пользователя не исполняются как SQL или tsquery. Скрытые товары и отзывы другого сетевого окружения исключены.

Приватные ключи кошельков платформы не нужны веб-серверу. Комиссия поступает напрямую на адрес платформы. Контракт EVM проверяет EIP-712 котировку, покупателя, сеть/адрес контракта, срок, допустимый токен и повторное использование заказа; разделение выполняется атомарно. Сервер Solana проверяет получателей, суммы, mint, сеть и memo заказа. Файл выдаётся только владельцу заказа после проверки платежа.

Solana RPC-ключ хранится только в `SOLANA_RPC_URL`. Авторизованный серверный маршрут готовит транзакцию из сохранённого заказа и выдаёт HMAC для её точного сообщения. При отправке проверяются владелец, срок, окружение, подпись покупателя, HMAC и полное совпадение инструкций с заказом. Клиент также сравнивает сообщение перед подписью. HTTP-ошибки RPC не раскрывают URL и тело ответа провайдера. При неопределённом результате отправки подпись сохраняется для сверки; явный отказ до отправки разрешает повторить оплату.

RLS включён для всех таблиц public, в том числе жалоб и журнала модерации. Скрытый товар читается клиентом только его продавца; произвольные изменения товара, цены, выплат и статуса оплаты через клиент Supabase запрещены. Жалобу читает только её автор, админский API закрыт allowlist. Скрытие ведёт журнал и запрещает новые заказы, но уже подписанная EVM-котировка действует до своего срока; оплаченные покупки сохраняют доставку.

Регистрация EVM-контрактов требует подтверждённого администратора и Origin. Сервер проверяет сеть, успешное создание, два подтверждения, точный deployment input с параметрами, наличие кода, неизменяемые адреса платформы и подписанта. Реестр закрыт от чтения/записи клиентским ролям и разделён по сети/окружению; API не заменяет существующие адреса. Каждый заказ хранит собственный router. Подпись Solana проверяется на неизменность сообщения транзакции перед broadcast. Разрешение ERC-20 выдаётся только на сумму заказа.

Локальный cache заказа включает ID покупателя, товар и окружение. Сервер и worker проверяют только своё окружение; тестовый заказ не блокирует mainnet-покупку. Перед подписью отображаются фактический аккаунт сайта, сеть, сумма и получатели. Смена аккаунта в расширении не подменяет подтверждённую сессию сайта.

Редактирование не меняет суммы и получателей уже созданного заказа. Файл и его метаданные заменяются одной транзакцией PostgreSQL; новые объекты R2 имеют отдельные ключи. Ранее выданные ссылки действуют до истечения своих 15 минут. Оплативший покупатель получает текущую версию товара при повторной загрузке. Временные staging-объекты следует очищать lifecycle-правилом отдельно от `products/` и `previews/`.

Идентификатор пользователя никогда не берётся из тела клиентского запроса. Служебные RPC доступны только серверу. Мутации API проверяют Origin, размер тела и лимиты запросов; Server Actions дополнительно проверяют сессию и владельца. Текст сообщений отображается через React без HTML-вставок. В R2 отключён публичный доступ; CORS для локального теста разрешает только `http://localhost:3000`.

Формат сообщения входа исправлен на ASCII statement, одноразовый случайный nonce и origin с правильным портом согласно [ERC-4361](https://eips.ethereum.org/EIPS/eip-4361). Solana получает каноническое сообщение в UTF-8, согласно [документации Phantom](https://docs.phantom.com/solana/signing-a-message).

## Оставшиеся эксплуатационные проверки

1. Заменить опубликованные ранее в переписке Supabase secret/service-role и R2 credentials в панелях провайдеров; сохранить новые значения только в серверном secret store. Публичные адреса и publishable key не являются секретами. Не отправлять seed-фразы или приватные ключи кошельков.
2. Развернуть PaymentRouter для включаемых EVM-сетей через `/admin` и проверить оплату каждого включённого актива, комиссию и партнёрскую выплату реальными кошельками. Независимый аудит контрактов, котировок и серверной проверки платежей не проводился. Инструкция первого малого платежа — в `MAINNET.md`.
3. Использовать отдельные production DB/bucket/кошельки, HTTPS, соответствующие Auth redirect/CORS, надёжные RPC, выбранное число подтверждений, резервные копии, мониторинг ошибок и worker сверки оплат. Проверить восстановление из резервной копии и ротацию котировочного ключа: signer контракта неизменяемый, при его замене нужен новый router.
4. Ограничить доступ операторов к ключам и панели облака, включить MFA у провайдеров. Для основной выручки использовать отдельный защищённый кошелёк. Приложение не хранит его ключ и не предоставляет API вывода средств.

Новые загрузки и замены проходят разрешённый список расширений, проверку имени, SHA-256, длины и сигнатуры содержимого до создания защищённой копии. Прямые EXE, скрипты, HTML/SVG и опасные двойные расширения запрещены; PE/ELF, переименованные в PDF/ZIP, отклоняются. Превью декодируются и перекодируются в WebP. Проверяется формат контейнера архива, а не каждый вложенный файл. PDF может содержать активное содержимое; существующие товары задним числом не пересканированы. Полноценный антивирус, разбор архивов и карантин не реализованы. Жалобы и скрытие помогают модерации, но не гарантируют безопасность скачанного файла.
