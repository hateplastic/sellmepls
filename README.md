# Sellmepls

Маркетплейс цифровых товаров с прямыми криптоплатежами. Next.js 16 App Router, TypeScript, Server Actions, Tailwind CSS, Framer Motion, Lucide, Supabase Auth/PostgreSQL, Viem/Wagmi, Solana web3.js, приватный S3/R2.

## Что реализовано

- Поиск по названию и описанию, фильтр категорий, сортировка по цене в USD, названию, оценке и числу отзывов. Пагинация сохраняет фильтры. [Поиск и тарифы](COMMISSIONS.md).
- Комиссия новых заказов: ниже $2.50 — 10%, от $2.50 — 5% + $0.50. Исторические заказы сохраняют прежние суммы и тариф.

- Вход по SIWE / SIWS через штатный Web3 provider Supabase. MetaMask и другие injected EVM-кошельки обнаруживаются через Wagmi; Phantom подключается для Solana. Вход требует подтверждения подписи в кошельке.
- Публикация ZIP, PDF, RAR, 7Z, документов, изображений, аудио и видео из списка разрешённых форматов. Проверяются имя и сигнатура содержимого; прямые исполняемые файлы и скрипты запрещены. Архив можно перетащить целиком. Обложка, ещё пять фото и YouTube-плеер, независимые цены по активам, публичная ссылка `/p/[id]`.
- Жалоба на товар, очередь жалоб в `/admin`, скрытие и восстановление с причиной и журналом действий. Скрытый товар недоступен в каталоге, новых заказах и партнёрских переходах; продавец не может снять ограничение. Проверка формата не заменяет антивирусное сканирование архива.
- Редактор `/dashboard/products/[id]/edit`: название, описание, категория, цены, партнёрская программа, замена файла и обложки. Адрес товара сохраняется; конфликт изменений в двух вкладках обнаруживается по revision. Старые заказы сохраняют суммы, покупатели получают текущую версию файла.
- 19 категорий цифровых товаров и фильтр каталога. Старые товары автоматически относятся к «Другое» и могут быть перенесены в редакторе.
- Личная переписка `/messages` по каждому товару, в том числе до покупки; история хранится в Supabase и доступна только участникам. Открытый диалог обновляется каждые 5 секунд. Повторная отправка одного запроса не дублирует сообщение.
- Админка `/admin`: оборот, комиссия, средний чек, оплаченные заказы, число пользователей/продавцов, активные продавцы за 30 дней и публикации за сегодня. Периоды 7/30/90 дней, дни Europe/Chisinau. USD рассчитывается по зафиксированному курсу заказа; testnet и mainnet учитываются отдельно.
- Кабинет с реальными товарами, продажами и доходом после комиссии. Разные токены и сети учитываются отдельно, без фиктивного суммирования ETH и USDC.
- Покупка через кошелёк, ограниченное разрешение ERC-20 на точную сумму, атомарный сплит между продавцом, платформой и партнёром, проверка сети и платежа сервером, восстановление по хешу и раздел покупок.
- QR открывает страницу товара на телефоне. Для подписи страницу нужно открыть в браузере MetaMask/Phantom. Это QR для перехода к полноценному checkout, а не QR обычного перевода, который обходит сплит.
- Приватные файлы, SHA-256, временные URL загрузки, неизменяемая копия товара при публикации, выдача файла на 900 секунд. Повторная выдача проверяет транзакцию заново.
- RPC polling в API и отдельном worker; общий rate limit в PostgreSQL; транзакционное создание заказов, идемпотентная регистрация оплаты и уникальность транзакции в сети.
- Dockerfile, конфигурация, компиляция и деплой контракта, инфраструктурный preflight, тесты RLS и платежей.

## Активы

| Сеть                         | Валюты           |
| ---------------------------- | ---------------- |
| Base, chain ID 8453          | ETH, native USDC |
| Arbitrum One, chain ID 42161 | ETH, native USDC |
| Solana mainnet-beta          | SOL, USDC, USDT  |

USDT на Base и Arbitrum намеренно не добавлен: непроверенные wrapped/bridged активы не подменяют нативный токен. Поддержка всех четырёх запрошенных валют есть, но не любая комбинация валюты и сети. Цены задаются отдельно, автоматического обмена нет. Для фиксированной комиссии $0.50 в ETH/SOL используется публичный Coinbase Exchange ticker с проверкой возраста последней сделки (до 60 секунд). При недоступном курсе такие заказы временно не создаются; USDC продолжает работать.

## Локальный запуск

Доступ к `/admin` разрешается только подписанным адресам из `ADMIN_EVM_WALLETS` / `ADMIN_SOLANA_WALLETS` (списки через запятую, серверные переменные). Изменение адреса выплат в профиле не меняет права. Для существующей базы после первоначального `schema.sql` выполните по порядку ещё не применённые миграции `20261014_product_editing.sql`, `20261014_messages_admin.sql`, `20261014_product_media.sql`, `20261014_mainnet.sql`, `20261015_moderation.sql`, `20261015_micro_fees.sql`, `20261015_catalog_search.sql` из каталога `migrations/`. В чистой базе достаточно актуального `schema.sql`.

Проверки и ограничения безопасности описаны в [SECURITY.md](SECURITY.md). Интеграционная проверка с временными аккаунтами и файлами: `npx tsx --conditions=react-server scripts/smoke-marketplace.mjs` при запущенном `npm run dev`. Она разрешена только на localhost:3000, по умолчанию в testnet; в mainnet добавьте `--allow-mainnet-no-payments`. Скрипт не совершает платежей и удаляет только свои тестовые записи/файлы.

Нужен Node.js 22.12+ и npm. Команды выполняются из корня проекта.

Сохраните `.npmrc` вместе с lockfile: он отключает автоматическую установку неиспользуемых optional peer SDK кошельков. Нужные React, Viem и Wagmi зависимости объявлены явно.

```sh
npm ci
cp .env.example .env.local
npm run setup:keys
node scripts/setup-inventory-key.mjs
npm run contracts:build
npm run dev
```

В PowerShell вместо `cp` можно использовать `Copy-Item .env.example .env.local`. Лендинг открывается без ключей, но работа с данными и платежами требует заполненной конфигурации. Тестовые товары и фиктивные продажи не создаются.

Все пустые значения в `.env.example` — реквизиты вашей инфраструктуры. Секреты не включены в исходный код. Next.js встраивает `NEXT_PUBLIC_*` при сборке; меняя их, пересоберите приложение. Никогда не помещайте service-role key, S3 secret, приватный ключ деплоя или URL с приватным RPC-ключом в `NEXT_PUBLIC_*`. Solana использует только серверный `SOLANA_RPC_URL`: `/api/solana/transaction` готовит и отправляет строго проверенный платёж авторизованного покупателя. Это не открытый RPC-прокси.

## Supabase

Поштучные товары (TXT, остатки, количество, пополнение, повторные покупки): [INVENTORY.md](INVENTORY.md). Для существующей базы добавлена миграция `20261015_inventory.sql` после `20261015_catalog_search.sql`. Её нужно применить до запуска обновлённого web/worker.

1. Создайте проект Supabase и выполните `schema.sql` в SQL Editor один раз на новой базе. Скрипт транзакционный; при ошибке не применяет частичную схему. Повторный запуск на существующей схеме не предназначен для миграции данных.
2. В Authentication → Providers включите Web3 Ethereum и Solana. Укажите Site URL и разрешённые Redirect URLs для вашего HTTPS-домена, включая пути приложения. Для разработки разрешите `http://localhost:3000/**`.
3. Заполните `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` и серверный `SUPABASE_SERVICE_ROLE_KEY`.
4. Сохраните резервное копирование БД и ограничьте доступ к service-role ключу.

Профиль создаётся на сервере из проверенного `auth.getUser()`. Адрес и сеть для входа берутся из `identities[].identity_data.custom_claims` провайдера `web3`. Редактируемый `user_metadata` не используется для подтверждения кошелька. Один валидатор читает этот формат на сервере и в кнопке входа.

EVM и Solana кошельки создают отдельные аккаунты Supabase. Продавец может указать оба адреса выплат в одном аккаунте. Это адреса получателей, введённые самим продавцом; дополнительное доказательство владения вторым адресом не запрашивается. При смене адресов ранее созданные заказы сохраняют первоначальных получателей.

RLS открыт для чтения активных товаров, собственных профилей и собственных продаж. Прямые клиентские INSERT/UPDATE/DELETE и вызовы служебных RPC запрещены. Все изменения проходят через серверную проверку пользователя. `product_files`, `uploads` и `rate_limits` не доступны anon/authenticated даже для SELECT.

## S3 / Cloudflare R2

Создайте **приватный** bucket. Для R2 отключите публичный `r2.dev` и публичный custom domain. Для AWS включите Block Public Access. Заполните `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`. Для R2: `S3_REGION=auto`, `S3_ENDPOINT` — S3 endpoint из панели Cloudflare. Для AWS оставьте endpoint пустым и задайте настоящий регион.

Серверному ключу нужны операции HEAD/GET/PUT/COPY для объектов в этом bucket. Для preflight нужен также HEAD bucket. Доступ браузера ограничен подписанным URL конкретного объекта.

Настройте CORS bucket:

- AllowedOrigins: точный origin из `NEXT_PUBLIC_APP_URL`; при разработке отдельно `http://localhost:3000`.
- AllowedMethods: `PUT`, `GET`, `HEAD`.
- AllowedHeaders: `Content-Type`, `Content-Length`.
- ExposeHeaders: `ETag`.
- MaxAgeSeconds: `3600`.

Для `staging/` настройте lifecycle expiration через 1 день. Для `products/` и `previews/` автоматическое удаление не включайте: оплаченные товары должны оставаться доступны. При аварии между записью объекта и фиксацией SQL могут оставаться неиспользуемые финальные объекты; удаляйте их только после сверки с `product_files`/`products` и достаточного периода ожидания.

Загрузка идёт прямо в bucket, URL действует 10 минут и подписывает размер/Content-Type. При публикации сервер потоково пересчитывает SHA-256, проверяет размер, декодирует разрешённое превью и перекодирует его в WebP без метаданных. Файл копируется с условием ETag в новый ключ, недоступный по upload URL. Повторное использование upload URL не изменяет проданный файл. Потоковая проверка SHA-256 работает независимо от различий checksum API между R2 и S3.

По умолчанию файл ограничен 100 MiB, превью — 5 MiB. `MAX_FILE_BYTES` позволяет поднять лимит до 1 GiB; браузер вычисляет хеш файла в памяти, поэтому учитывайте память устройств покупателей/продавцов. На serverless хостинге задайте достаточные лимиты времени Server Actions и памяти для обработки превью. Файлы выдаются как `application/octet-stream` с `Content-Disposition: attachment`; проверки на вредоносное содержимое в сервисе нет.

## EVM контракт

`contracts/PaymentRouter.sol` — неизменяемый контракт без администратора и вывода чужих средств. Адрес платформы, адрес подписанта цены и whitelist токенов фиксируются в конструкторе. EIP-712 подпись сервера связывает order ID, покупателя, продавца, токен, суммы, партнёра, deadline, chain ID и адрес контракта. Нативный платёж делится на два или три перевода; ERC-20 переводится напрямую от покупателя через `SafeERC20`. Неудача любой части откатывает всю операцию. Проверяется фактическое приращение токенов у получателей. Покупка самого у себя запрещена.

Ключ использованного заказа включает покупателя: посторонний кошелёк не может заблокировать чужой публичный order ID. Бэкенд дополнительно сверяет сумму, сеть, токен, продавца, покупателя и время с неизменяемым заказом БД.

1. Заполните `BASE_RPC_URL`, `ARBITRUM_RPC_URL`, `PLATFORM_EVM_WALLET`; создайте `QUOTE_SIGNER_PRIVATE_KEY` через `npm run setup:keys`.
2. Выполните `npm run contracts:build`.
3. Установите `DEPLOYER_PRIVATE_KEY` только в окружении отдельного процесса деплоя. Для mainnet деплой требует ETH и расходует gas. Приложению и worker этот ключ **не нужен**.
4. Выполните `npm run contracts:deploy -- base` и `npm run contracts:deploy -- arbitrum`.
5. Запишите выведенные адреса в `BASE_PAYMENT_ROUTER` / `ARBITRUM_PAYMENT_ROUTER`, уберите приватный ключ из окружения.
6. Сохраните скомпилированный artifact и lockfile этого деплоя. Preflight сравнивает runtime bytecode с локальным artifact, исключая места immutable-полей.

По умолчанию достаточно одного включения в канонический блок. Это не L1-finality Base/Arbitrum; реорганизация после выдачи файла не позволяет отозвать уже скачанный файл. Для более строгой политики увеличьте `EVM_CONFIRMATIONS`. Формула комиссии: `floor(amount * 500 / 10000) + fixedFee`; продавец получает остаток после комиссии партнёра. Подписант цены — отдельный серверный ключ без средств. Его приватный ключ нужен приложению, но не публикуется и не является приватным ключом платформы. Компиляция контракта нацелена на Cancun.

## Solana

Заполните `SOLANA_RPC_URL`, `PLATFORM_SOLANA_WALLET` и публичный RPC для браузера. Адрес платформы должен быть обычным on-curve кошельком. Сервер проверяет полный genesis hash выбранного окружения — Devnet или mainnet-beta. Приватный ключ платформы не используется.

SOL: два или три SystemProgram transfer и memo заказа в одной транзакции. USDC/USDT: идемпотентное создание ATA получателей, два или три `TransferChecked`, memo. Покупатель оплачивает network fee и rent для новых ATA. Поддерживается стандартная SPL Token программа, без Token-2022 и произвольных токенов. Минимальные инструкции ABI находятся в `lib/spl.ts`.

Проверяются подписант/fee payer, memo, точные суммы и mint, стандартные ATA, authority, отсутствие чужих программ и успех всей транзакции. По умолчанию используется commitment `confirmed`; `SOLANA_COMMITMENT=finalized` усиливает политику. Solana не имеет нашего on-chain состояния использованных заказов: ручная повторная отправка другой транзакции может повторно перевести средства, хотя БД повторную продажу не создаст. UI не предлагает повторно оплачивать заказ с уже сохранённым хешем.

Срок предложения в UI — 10 минут. EVM-контракт проверяет deadline. Solana System/SPL программы не поддерживают этот deadline, поэтому сервер принимает корректный поздний Solana-платёж по неизменяемым условиям его заказа, чтобы покупатель не потерял право на файл после долгого подтверждения в кошельке.

## Фоновая проверка

При получении хеша `/api/verify-tx` сохраняет его до RPC-проверки. Браузер повторяет проверку каждые 5 секунд до 10 минут; фон продолжает независимо от открытой страницы.

Запустите отдельный долгоживущий процесс из этого checkout:

```sh
npm run worker
```

Либо настройте планировщик хостинга на `POST /api/reconcile` каждую минуту с заголовком `Authorization: Bearer` и значением `CRON_SECRET`. Секрет сгенерируйте криптографически случайным, не менее 32 символов. GET специально не поддерживается. Одновременные проверки безопасны: SQL блокирует заказ и уникальность hash.

Worker проверяет хеши, переданные серверу. Если кошелёк отправил транзакцию, но вкладка закрылась до передачи хеша, откройте заказ и используйте «Восстановить платёж по хешу». Сервис не сканирует всю историю всех кошельков. Подписанный Solana hash сохраняется локально до broadcast. Неподтверждённый платёж никогда не выдаёт файл.

## Проверка и production deployment

```sh
npm run typecheck
npm test
npm audit
npm run contracts:build
npm run preflight
npm run build
npm start
```

Preflight требует настоящие сервисы и проверяет RPC сети, bytecode, получателя и подписанта контрактов, доступность таблиц и bucket. Он не отправляет платежей. Локальные тесты используют настоящий PostgreSQL через PGlite и локальную EVM; фальшивые данные используются только в тестах.

Для Vercel/Node-хостинга задайте все env из `.env.example`, включите HTTPS, настройте scheduler или отдельный worker. Для Docker передайте публичные переменные как build arguments, серверные секреты только как runtime environment. `Dockerfile` собирает standalone Next.js и запускает его от пользователя `node`. В Docker image веб-сервера worker не включён; для сверки используйте защищённый API scheduler либо отдельный процесс checkout.

До приёма реальных продаж проведите сквозной тест на вашей инфраструктуре: вход обоими типами кошельков, загрузка/публикация, покупка каждого включённого актива, реальный сплит, рестарт приложения, повторное скачивание, проверка RLS внешним anon ключом. Внешние аккаунты и облачная инфраструктура в этой поставке не создавались. `setup:keys` создаёт только локальные секреты приложения. Локальные тесты и сборка не являются независимым аудитом смарт-контракта.

## Первый запуск и тестовые сети

Начните с [TESTING.md](TESTING.md): там указано, где получить реквизиты и бесплатные тестовые токены. По умолчанию `NEXT_PUBLIC_CHAIN_ENV=testnet`: Base Sepolia (84532), Arbitrum Sepolia (421614), Solana Devnet. ETH/SOL и USDC используют соответствующие тестовые сети и адреса Circle. USDT в testnet выключен. Таблица mainnet выше относится только к `NEXT_PUBLIC_CHAIN_ENV=mainnet`.

Окружение каждого заказа хранится неизменяемым: заказы, проверка, worker, доходы продавцов/партнёров и админская аналитика разделены по `chain_environment`. Профили, товары, чат и переходы общие для экземпляра сайта. Для полной изоляции staging и production используйте отдельные Supabase проект и bucket. После изменения публичных переменных пересоберите приложение. При переключении окружения старые покупки открываются только в соответствующем окружении; данные не удаляются.

`npm run setup:keys` сохраняет случайные `CRON_SECRET`, `REFERRAL_SECRET`, `QUOTE_SIGNER_PRIVATE_KEY` в `.env.local`, не выводя секреты и не заменяя существующие значения. Схема предназначена для новой БД: в этом проекте прежняя версия с комиссией 2% ещё не разворачивалась во внешнем Supabase. Старые платёжные контракты несовместимы с новыми заказами, нужен новый деплой.

## Партнёрская программа

- Публичные витрины `/s/[id]`, имя и описание автора, рейтинг из подтверждённых покупок, отзывы с ответами продавца, комментарии.
- Продавец включает программу отдельно для каждого товара и задаёт 1–90% с точностью 0.01%. Проверяется, что цена оставляет продавцу положительный остаток после всех комиссий.
- Ссылки `/r/[code]` на товар или витрину, отдельные именованные кампании для Instagram/Telegram и других каналов, копирование, публикация и QR.
- Кабинет `/affiliates`: переходы, лиды, подтверждённые продажи, уже выплаченные суммы и хеши. Партнёр настраивает кошельки в разделе «Профиль и выплаты». Выводить деньги из платформы не нужно.

**Пример:** товар 10 USDC, партнёру 10%. Платформе 1 USDC ($0.50 + 5%), партнёру 1 USDC, продавцу 8 USDC. Без партнёра продавцу 9 USDC. Покупатель платит указанную цену и сетевые расходы. Процент партнёра берётся от полной цены, а не от остатка после платформы.

Вся арифметика целочисленная: процент платформы и партнёра округляется вниз, фиксированная комиссия — вверх до минимальной единицы токена. USDC/USDT учитываются по договорной единице $1 = 1 токен; изменение привязки не пересчитывается. В testnet рыночный курс ETH/SOL нужен для реалистичного расчёта, но тестовые токены не имеют денежной стоимости. Курс, суммы и получатели фиксируются в заказе.

Последний подходящий переход за 30 дней сохраняется в подписанной HttpOnly cookie. Витринная ссылка учитывает только товары этого продавца с включённой программой. Готовый заказ сохраняет своего партнёра и процент, даже если позже изменены условия или программа отключена. Новые заказы используют текущие условия. Собственный аккаунт или совпавший кошелёк не получают партнёрскую комиссию; владение несколькими разными кошельками без установления личности распознать невозможно.

Переходы дедуплицируются по браузеру на ссылку в сутки. Лиды — разные пользователи, начавшие атрибутированный заказ. Продажи — только подтверждённые оплаты. Это браузерная аналитика, не доказательство уникального человека: очищенные cookies и боты влияют на переходы. Сырые IP не сохраняются, rate limit использует HMAC. На reverse proxy заменяйте присланный клиентом `X-Forwarded-For` доверенным значением.

Атрибуция действует в одном браузере; QR сохраняет партнёрскую ссылку при переходе на другое устройство. Автоматической склейки устройств нет. Отзывы доступны только после проверенной покупки, один на покупателя и товар, с возможностью обновления. Продавец может ответить, но не удалять чужие отзывы. Комментарии доступны авторизованным пользователям и удаляются их автором. Спам ограничивается серверным rate limit.

Таблицы партнёров, кликов, отзывов и комментариев закрыты RLS для прямых изменений. Партнёр может читать только собственные ссылки. Данные покупателей не раскрываются партнёрам: сервер отдаёт агрегаты и сведения об их выплатах. Публичные страницы выбирают имя автора, тексты, рейтинг и даты, без приватных файлов и реквизитов аккаунта.
